# Changelog

All notable changes are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The version is the same in `plugins/frc/.claude-plugin/plugin.json` and in every `pyproject.toml` under `plugins/frc/`.

## [Unreleased]

- Live and log parity: `nt4_scan` runs on a few seconds of the live robot the same usual-trouble checks `wpilog_scan` runs on a log (battery and brownouts, loop time, link and CAN numbers), found by the same naming rules. The scan, the topic roles and the loop and CAN checks moved into shared code (`frc_mcp_wpilib`), and `wpilog_scan` no longer carries a swerve block: `wpilog_swerve` is the one tool for the modules. A live scan has no log text, no enabled periods and no stopped-signal check, and says so. `tests/common/test_parity.py` fails when a tool in either server has no partner and no stated reason. **`nt4_scan` is tested against a local NetworkTables server, not a real robot.**
- Swerve drivetrains, first tier: `wpilog_swerve` compares each module's measured state with its commanded one while the robot was enabled (speed error, angle error while it was told to move, top speed) and flags a module whose p95 error is at least twice the typical one and not tiny. It finds the arrays only by name convention (AdvantageKit `SwerveStates/Measured` with `SetpointsOptimized` or `Setpoints`; CTRE `DriveState/ModuleStates` with `ModuleTargets`) and lists other `SwerveModuleState[]` topics as candidates. `nt4_swerve` does the same live: it records both arrays for a few seconds while the robot is driven. The comparison is shared code in `frc_mcp_wpilib.swerve`. A recording with fewer than 10 comparable updates says so instead of calling the drivetrain clean. New skill `wpilib-swerve` covers both; `frc-explain` has a swerve note. **Checked on synthetic logs only; the topic names come from AdvantageKit and CTRE documentation, and the lag thresholds are rules of thumb. YAGSL's plain-number arrays are not read, and the check is module-level: a wrong encoder offset or a bad gyro is not visible. `nt4_swerve` is tested against a local NetworkTables server, not a real robot.**
- Docs: the four biggest guides are split so none is overwhelming (each file stays under 2,000 words, which a test now enforces). `ARCHITECTURE.md` now has `ARCHITECTURE_SERVERS.md` and `ARCHITECTURE_NOTES.md`; `SETTINGS.md` has `SAFETY.md`; `WPILOG.md` has `WPILOG_ADVANCED.md`; `CTRE.md` has `CTRE_DEVICES.md`; `NT4.md` has `NT4_ADVANCED.md`. `docs/README.md` is a map of all guides. Links and anchors were repointed; nothing was rewritten.
- `wpilog_scan` now checks loop time and CAN errors. `loop` gives the median, p95 and worst loop time while enabled (AdvantageKit's `LoggedRobot/FullCycleMS`, with `UserCodeMS` beside it; the slow boot cycle is left out) and flags a p95 over the 20 ms period; a loop-time topic with only a suggestive name is listed as a candidate. `can_bus` gives, per bus, the utilization, the TEC and REC levels and the rise in bus-off and TX-full counts while enabled, found by exact field name under a CAN path (the old guess for CAN utilization in `link` is gone, so a topic like `scanUtilization` no longer counts); a bus-off while enabled is a high flag, an error-passive level (128+) a medium one. **Checked on synthetic logs only; the AdvantageKit and WPILib field names come from their published documentation, not from a real log seen here.**
- A log whose file is replaced or gets shorter after it was opened no longer answers from its old index: every query on it fails with "changed on disk ... call wpilog_open on it again" (before, only a read that needed the file did; a synced view names the file that changed). A log that only grows, as one still being recorded does, keeps answering from the records it was opened with, and opening it again warns once that earlier answers came from the old file. Replacement is told from growth by size and a hash of the first 64 KB. **Tested with appended and shortened files, not with a log being written by a robot.**
- `wpilog_open` shows which robot code made a log (`code`): the text topics `GitSHA`, `GitBranch`, `GitDirty`, `GitDate`, `BuildDate`, `ProjectName` and `Version` (the last only under a `metadata` path), as AdvantageKit's `BuildConstants` logs them. A warning names the paths when `/RealMetadata` and `/ReplayMetadata` disagree, and `wpilog_diff` adds `code` and a warning when the two logs come from different code (whatever the filter). **Checked on synthetic logs only; not on a real AdvantageKit log.**
- Tests: the log server is now also checked against a second WPILOG reader written from the format spec (`tests/wpilog/independent_log.py`) and against Python's `statistics`: topics, counts, every value (a 6-byte timestamp, a late topic, UTF-8 text), a struct and an array, summary numbers and the time-weighted mean. **Synthetic logs only, built with our own writer from the same spec; not checked against a real match log.**
- `summary` replies now say how a signal is logged: `sampling` is `periodic`, `change_only` or `event` (signals with at least 10 updates). A mean over a `change_only` signal counts updates, not seconds, so `reduce=time_weighted` is the mean over time. **The 80% / half-median-gap thresholds are rules of thumb, not checked against a real match log here.** Topics that share one value get it once in `all`.
- New skill `frc-reasoning`: nine rules for explaining a cause from robot data without overclaiming (answer first, quote only returned numbers, empty is not clean, a name is not proof, check the event happened, fact / inference / hypothesis, test a rival cause, no hand statistics, say when a log was cut short), with `references/why.md`. `wpilib-triage`, `wpilib-log-analysis`, `wpilib-live` and `frc-explain` point to it, and `match-log-analyst` carries the short form (a subagent cannot load skills). **Not tried in a live headless run yet; the examples in `why.md` are illustrations, not cases seen with this toolkit.**
- A reply that is not a full answer now says so: `status` is `no_match` (every topic failed, or there was nothing to search) or `partial` (some failed), with a `hint` that finding nothing is not proof of no problem. It is on `wpilog_query`, `wpilog_get_values`, `wpilog_text`, `nt4_get_values` and `nt4_get_widgets`; a good reply has no `status`, so it costs no tokens. **Not yet added to the other tools** (`wpilog_when`, `wpilog_scan`, the other servers), which use their own `checked` and `err` forms.
- `wpilog_scan` no longer guesses the battery. It uses a topic only when you pass `battery=` or the name follows a convention (`BatteryVoltage`, or `Voltage` under a PowerDistribution, PDH, PDP or Battery path). A topic with only a suggestive name is listed as a `candidate` with a hint, and a brownout flag with a look-alike name as `brownout_candidates`. The reply says how each choice was made (`chosen_by`, `others`, `link.from`).. **The conventions come from published logging documentation and our own logs; not checked on a real match log.**
- Learning mode: a new plugin setting (`learning_mode`, off by default, sets `FRC_LEARNING_MODE` on every server). While on, replies from read-only tools gain one `learn` key: a short statement that explains why something works or shares something interesting, to spark curiosity (never a question) (`learn_tips.py`), once per tool per session. Tool descriptions and schemas do not change, so the token budget is untouched. `frc-explain` is now a step-by-step teaching guide (explain why, show it in their data, invite curiosity without quizzing) with `references/concepts.md`. **Not tried with real students or a live model run yet:** the tip wording and the skill are untested beyond the unit tests.

- `wpilog_scan`: one call that checks a log for the usual trouble (errors, loop overruns, battery sag and brownouts, packet loss and CAN use, signals that stopped) and returns ranked `flags`, saying what it could not check. The `scan_match` prompt uses it. **Checked on simulation and synthetic logs only, not on a real match log** (the real logs available were long simulator sessions with no battery or Driver Station data): the checks, thresholds and topic names (`battery`, `brown`, DS-log and SystemStats names) are rules of thumb and assumptions.
- New `reduce` values on both servers: `peaks` (biggest spikes and dips, one per event) and `buckets` (min, max and mean per time slice, so spikes survive).
- `wpilog_query by_mode=true` (one answer per enabled period), `wpilog_when sample=[...]` (other topics at the start of each stretch) and `a|b` in `name_contains` for topic and text searches.
- `peaks` reports the `median` and lists `high` (above it) and `low` (valleys, below it), so reverse spins and sparse data read correctly. `wpilog_scan` calls many signals stopping together a low flag (a finished test sequence), not one fault each. `nt4_inspect` with no arguments lists the clients. `name_contains` takes `a|b` on the NT4, log, simulation and VS Code servers alike (so `sim_output name_contains="error|exception"` works). `sim_stop` and the time limit mark a non-zero exit code as expected and do not count shutdown error lines.
- The reply ceiling was re-checked on a 570-topic synthetic log: kept at 12000 characters.
- `nt4_health`: a Systemcore's own health (port 6810) in one call, with ranked `flags` and what it could not check, like `wpilog_scan` for the live robot. `wpilib-prematch` and `systemcore-live` use it. **Seen on a real Systemcore** (image alpha18, over Wi-Fi at 172.30.0.1, healthy): the topic names and types, the alert paths (`/Netcomm/Alerts/<group>/<level>/<name>/active`) and `/diagnostics/canbusutil` (two numbers per bus: percent, then the same as a fraction). Fault, brownout and low-battery paths were tested only against a local NetworkTables server, and the limits are rules of thumb. `/diagnostics/canbuserr` and `canbushealth` have no documented meaning, so they are shown or ignored, never flagged.
- The log server can read a log (or list a folder of logs) outside the project folder: the plugin setting "Read logs from other folders" (`WPILOG_ALLOW_OUTSIDE`) is on, and a second `PreToolUse` hook (`frc-mcp hook ask-outside`) makes Claude Code ask the person before every such `wpilog_open` or `wpilog_list folder=`. Log files only, read only, never a drive root or home folder. Checked in a headless run: the prompt appears and, with nobody to answer, the call is denied. Not verified: `bypassPermissions` mode.
- Not done: opening `.hoot` straight from `wpilog_open` (a read tool would have to run Owlet, and servers must not import each other).

## [0.1.0] - not yet released

First release.

What it can do:

- Live NetworkTables 4 server: connect, list topics, read and write values (writes are off by default), watch and capture signals, reduce them to numbers (summary, percentiles, step response and more), triggers and events, and struct and protobuf decoding.
- Safety and size: read-only by default, short tool descriptions, a core toolset, a `check` command, prompts and resources.
- Log server: reads `.wpilog` files and Driver Station logs with the same reducers, finds when a condition held, compares logs, and lines up several logs on one clock.
- Practice robot and practice log (`demo robot`, `demo log`) for learning without hardware.
- Eighteen skills for students, from `frc-start-here` (where to begin) to task skills such as `wpilib-project`, `wpilib-live`, `wpilib-log-analysis`, `systemcore`, `systemcore-live` and `ctre-diagnose`. New since the first draft: `wpilib-prematch` (read-only pit check), `wpilib-triage` (log to a one-page "fix first" report), `wpilib-tune` (measure a loop with `step_response` and `peaks`) and `frc-explain` (explains a result in plain words and asks one question).
- WPILib 2027 (alpha-8) support: `wpilib-project/references/2027.md` (renames and removals, OpModes, Commands v3, Telemetry and Tunables, gamepads, simulation); `wpilib-build` and `wpilib-live` know the Java 25 and import rules; the WPILib install folder on Linux also looks in `$XDG_DATA_HOME/wpilib`
- `sim_start` uses the Gradle `run` task by default for a 2027 project and refuses `simulateJava` there, because GradleRIO 2027 made `simulateJava` fail on purpose (checked on a real alpha-8 project)
- `systemcore-live` reads a real Systemcore's health (`/sys`), CAN buses, robot-code state and alerts from its private NT4 server on port 6810, with no SSH (seen on a real Systemcore). The NT4 server never writes to that port, even with the write settings on
- Subagent `match-log-analyst`: reads `.wpilog`, `.hoot` and JFR files with read-only tools in its own context and returns a short summary of what happened, when, the likely cause and the evidence
- CTRE servers: tool version manager, Owlet (`.hoot` to `.wpilog`), passerine (MIDI to CHRP), caniv (CANivore) and the Phoenix Diagnostic Server reader.
- Tests, mypy and ruff on Linux, Windows and macOS, plus evaluations with a model.
- Live server details: WebSocket connect and clock sync through ntcore, struct, msgpack and protobuf decoding, publishers with properties and set-default writes, `periodic`, `all` and `prefix` subscriptions, and meta-topics (`nt4_inspect`). Reducers: `summary`, `time_weighted`, `changes`, `samples`, `edges`, `durations`, `percentiles`, `rate` and `step_response`. Triggers and an event inbox, conditions on several topics (`also`), widget groups, honest handling of connection gaps and dropped history, and units on values.
- Log server extras: `wpilog_sync` (matches enable and disable edges, falls back to wall clock; tested on generated logs only), Driver Station logs (`.dslog` and `.dsevents`; format taken from AdvantageScope's reader, not checked against a real Driver Station), and the prompts `review_match`, `find_problems` and `scan_match`.
- Not planned: secure `wss:` on port 5811 (pyntcore has no TLS; the server explains this) and a raw protocol inspector.

Changes and fixes made while getting ready for this release:

- License: AGPL-3.0 (`LICENSE`), with `THIRD_PARTY_NOTICES.md` listing what the servers use and the trademarks involved.
- Evaluations: no question set for a real robot ships any more. `evaluations/make_sim_eval.py` writes a read-only question set, with computed answers, from any robot simulation you start yourself.
- Open-source basics: `SECURITY.md` (private reporting), a pull request template, and issue forms for bugs, feature requests and safety concerns. The marketplace entry is pinned to the release tag, and the repository is named `frc-agent-toolkit`, while the plugin and its marketplace are named `frc-toolkit` (the `frc-mcp` command is unchanged).
- Docs: one guide per server. `CTRE_DIAG.md` is part of `CTRE.md`; `ROADMAP.md`, `LEARNING.md` and `evaluations/BENCHMARKS.md` are gone (open ideas are in CONTRIBUTING, benchmarks in `evaluations/README.md`).
- Host keys are trusted only by a person at a terminal. **Removed the `systemcore_ssh_trust` tool**; the new command `frc-mcp systemcore trust <host>` prints the fingerprint, says whether the OS image changed, and pins the key only after you type the first 8 characters of the fingerprint (it refuses when input is not a terminal). `systemcore_provision` no longer takes `fingerprint` and uses only the default login password; with your own password, run `frc-mcp systemcore provision`, which asks for the same confirmation. A changed-key message now names that command.
- The robot-network check resolves names for IPv4 and IPv6, needs every address to be private, and the servers (Systemcore, Phoenix Diagnostic Server) then connect to the checked address instead of looking the name up again.
- `systemcore_connect` joins no Wi-Fi when a password is saved but `SYSTEMCORE_WIFI_SSID` is not (an impostor `SYSTEMCORE...` network could take the password). Windows join: the temporary profile file is in a private folder removed on exit, and a profile added by a failed join is deleted.
- Systemcore: the SSH host-key probe has a connect timeout; the support bundle download stops at `SYSTEMCORE_MAX_DOWNLOAD_MB` (default 200) and deletes the partial file; an OS image of the right size is re-downloaded when its SHA-256 does not match the release list.
- Risky tools (deploy, restart, record, delete logs, install, flash) are off until you turn on an `*_ALLOW_*` setting.
- Tools behind an `*_ALLOW_*` setting are hidden while it is off (11 tools: `nt4_set_value`, `nt4_release_publisher`, `wpilib_deploy`, `jfr_record`, `ctre_install`, `caniv_configure`, `caniv_flash` and four Systemcore restart and SSH tools), so the assistant does not try what it cannot use and about 1,600 fewer tokens load in every session. They appear when you turn the setting on. Each tool still refuses on its own. `systemcore_logs_prune` (its dry run works without the setting) and the Wi-Fi tools stay listed.
- Security fixes: the SSH key is made owner-only from the start, JFR recordings keep secrets out, and a restart is refused when the robot state is unknown.
- Closing `.wpilog` logs no longer blocks the server.
- Everything lives in one uv workspace under `plugins/frc/`: `servers/` for the eleven servers and `lib/` for shared code.
- One command, `frc-mcp`, starts any server (`frc-mcp nt4`), checks your setup (`frc-mcp doctor`) and runs the practice robot and log (`frc-mcp demo`).
- Servers have short keys such as `nt4`, `wpilog` and `ctre-diag`.
- The plugin asks for 13 settings. Folders follow your project, and on/off settings are real switches.
- Skills: 18 became 14 (`systemcore`, `systemcore-provision`, `ctre-diagnose`, `ctre-convert`, `wpilib-project` and `wpilib-live` are merges; the build and deploy skill is split into `wpilib-build` and `wpilib-deploy`). Skills that change things (`systemcore-restart`, `systemcore-provision`, `ctre-canivore`, `wpilib-deploy`) run only when you ask. Descriptions are shorter, so less is loaded in every session.
- The NT4 and log servers describe their shared parameters (`since_ms`, `until_ms`, `field`, `also`, `include_hidden`, `prefix`) with one shared type each, so the wording cannot drift; a test checks it. About 40 fewer tokens load in every session.
- Server instructions are shorter and say what each server is for and which sibling to use instead (the live-values and log servers, simulation and VS Code, the Systemcore and its logs, the two CTRE device servers). All eleven together are under 2,800 characters (about 540 tokens instead of about 820); a test caps each at 250. Several tool descriptions now start with the words a student would search (for example "Robot values now", "Compare two logs", "Robot console output"), with no more description tokens in total. A test checks that no tool asks to be always loaded.
- If `ENABLE_TOOL_SEARCH=false` is set where your assistant starts, a server with no `*_TOOLSET` setting uses `core` instead of `full`; an explicit `*_TOOLSET` still wins.
- Startup is lighter: paramiko, ntcore and protobuf load only when used.
- First start is safer: a `SessionStart` hook runs `uv sync` quietly so the servers find their Python environment ready (it prints nothing; if it is slow, the servers still set themselves up).
- Confirm first: a `PreToolUse` hook makes Claude Code ask a person before each call of a tool that changes something (NT4 writes and releasing a publisher, deploy, changing the project's vendor libraries or team number, recording with JFR, live JFR attach, installing a CTRE tool, configuring or flashing a CANivore, restarting robot code, rebooting, provisioning or forgetting the SSH key, deleting logs, the support bundle, and Wi-Fi connect and disconnect). Read-only tools are not affected; the `*_ALLOW_*` switches stay the real boundary. New command `frc-mcp hook ask "<reason>"` prints the answer.
- Plugin metadata, version checks and this changelog were added.
