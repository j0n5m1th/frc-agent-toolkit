# Functional tests

**These are not unit tests and are not part of the pytest suite or CI.** They check that each *installed* MCP server works as an assistant would use it: the console command starts, the MCP handshake succeeds over stdio, and the tools return the right answers. All 11 servers are covered (the same names as `frc-mcp <key>`: `wpilog`, `nt4`, `sim`, `vscode`, `jfr`, `systemcore`, `ctre-tools`, `ctre-owlet`, `ctre-passerine`, `ctre-caniv`, `ctre-diag`).

**Tools behind a switch are hidden, not refused.** While its `*_ALLOW_*` switch is off (`VSCODE_ALLOW_DEPLOY`, `JFR_ALLOW_RECORD`, `CTRE_ALLOW_INSTALL`, `CANIV_ALLOW_CONFIG` / `CANIV_ALLOW_FLASH`, `SYSTEMCORE_ALLOW_PROVISION` / `SYSTEMCORE_ALLOW_RESTART`, and for NT4 `NT4_ALLOW_WRITES` with `NT4_WRITE_PREFIXES` and without `NT4_READ_ONLY`), the tool is not listed and calling it by name fails with an unknown-tool error. So each test checks the short list first, then starts the server again with the switch in its environment and checks the full list and the old refusals and results (`harness.is_unknown_tool` and `harness.tool_names`).

- `wpilog_server.py` runs `mcp-wpilib-wpilog` against the deterministic practice log written by `evaluations/fake_log.py` (30 s match; the expected values come from that file).
- `nt4_server.py` runs `mcp-wpilib-nt4` against `evaluations/fake_robot.py`, which it starts on a free local port and stops afterwards. It covers reads, waits, widgets, the write tools (hidden by default, hidden without a prefix and in read-only mode, listed and working with writes on, and a write outside the allowed prefixes refused), captures, saving a capture to a `.wpilog` that the log server then opens, and read-only mode.
- `sim_server.py` runs `mcp-wpilib-sim` against the minimal project folder `harness.make_project` writes: the idle status with its settings, and the refusals. Gradle itself does not run.
- `vscode_server.py` runs `mcp-wpilib-vscode` against the same minimal project: `wpilib_info`, `wpilib_set_team`, `wpilib_deploy` hidden until `VSCODE_ALLOW_DEPLOY=1` (then a bad team number is refused before Gradle runs), and `VSCODE_TOOLSET=core`.
- `jfr_server.py` runs `mcp-jfr` over a folder with one `.jfr` file: the tool list (`jfr_record` is hidden until `JFR_ALLOW_RECORD=1`, then a too-long recording is refused before any JVM tool runs), the prompt, `jfr_list`, and `JFR_TOOLSET=core`. The tools that parse a recording need the JDK's `jfr` binary and stay in the pytest suite.
- `systemcore_server.py` runs `mcp-systemcore` against `systemcore_fake.py`, a fake controller on local ports: its four HTTP services, the UDP discovery answer, and a real SSH and SFTP server (`SYSTEMCORE_PORTS` points the server at them). It covers `init`, discovery, the tools hidden while their switches are off (provision and forget, restart and reboot), the health summary with and without the SSH key, installing the key with `systemcore_provision` (the fake controller accepts only the documented default login password, `systemcore`, for that one step; a custom `SYSTEMCORE_PASSWORD` in the `.env` file is refused over MCP and the user is sent to `frc-mcp systemcore provision`, without the password being repeated), host-key pinning and an OS-update key change (the assistant has no trust tool: the person confirms a changed key at the terminal with `frc-mcp systemcore trust`, which the test does through the same state call because a terminal cannot be driven here), listing, downloading and pruning logs (with the refusals), the support bundle, the OS release comparison from a saved list, `check`, and `SYSTEMCORE_TOOLSET=core`. Fetching the real GitHub release list, the update file download, and the Wi-Fi join (it changes this computer) stay in the pytest suite.

  **Fake or real:** by default (`--target auto`) a real Systemcore is used if exactly one answers on the network (or pass `--host`), otherwise the fake one. A real run is **read-only**: it never installs a key, joins Wi-Fi, deletes, trusts or forgets a host key, or builds a bundle, and it works on a temporary copy of your state folder (your key and pinned host keys), so your own files are not changed; checks that need the SSH login are skipped, with the reason, if the key is not installed. `--target fake` and `--target real` force one (real fails if none answers).
- `ctre_tools_server.py` runs `mcp-ctre-tools` with the index copy bundled in the package and a temporary tools folder: the tool list, the status and version answers (levels to fill, how to set a project), `ctre_install` hidden until `CTRE_ALLOW_INSTALL=1` (then the refusals for a version with a compliancy, `fill_gaps` with a version, and a version CTRE does not list; nothing written). Downloads need CTRE's real https host, so they stay in the pytest suite, except under `--live`: that refreshes the index from CTRE's real website and runs `fill_gaps` into a temporary folder (about one index request and three downloads, spaced a second apart, deleted afterwards).
- `ctre_owlet_server.py` runs `mcp-ctre-owlet` with `fake_owlet.py` installed behind a tiny launcher as "Owlet 26.3.0" (it behaves the way the real Owlet was seen to, see [docs/CTRE.md](../docs/CTRE.md), and writes a real `.wpilog`). It covers the tool list, the exact-level rule and the install command when no Owlet fits, signals through real child processes, conversions (only chosen signals, never overwriting, a bad signal id refused, an Owlet that reports success without a file), and opening the converted file with the log server. Running the real Owlet on a real log stays a manual check. `ctre_support.py` holds the workspace, the hoot file and the launcher that installs a stand-in tool; the passerine and caniv files use it too.
- `ctre_passerine_server.py` runs `mcp-ctre-passerine` with `fake_passerine.py` installed as "passerine 1.0.0" (it behaves the way the real one was seen to, including silently overwriting an output): the tool list, listing MIDI and CHRP files, a real conversion through a child process, the refusals (overwrite, a name that leaves the folder, a file that is not MIDI), a run that reports success without writing a file, and no leftover files.
- `ctre_caniv_server.py` runs `mcp-ctre-caniv` with `fake_caniv.py` installed as "caniv 1.1.1.0" (its list layout, info and license lines, and `-102` / `-206` errors are what the real caniv printed with a CANivore connected, with made-up values; only what rename, reset and flash print is its own) and a log of every call it receives. It proves what ran and what did not: the two change tools are not even listed without `CANIV_ALLOW_CONFIG` / `CANIV_ALLOW_FLASH` (each switch lists only its own tool), never for an unlisted device or `*`, flashing only CANivore `.crf` files from the firmware folder, and `CANIV_TOOLSET=core`. On macOS it only checks that caniv is reported as not available.
- `ctre_diag_server.py` runs `mcp-ctre-diag` against `evaluations/fake_diag.py`, a real HTTP server on localhost that answers the way the real Phoenix Diagnostic Server was seen to (shapes, error codes, an error inside an HTTP 200): the tool list, device and fault shaping, live values, config differences, bus counters, ambiguous device names, the address check, and a proof that only read actions and the blink were ever sent. With `--host <address>` it runs READ-ONLY checks against a real controller (for example `--host 172.30.0.1`): nothing is blinked or changed.
- `harness.py` is the shared client, PASS/FAIL reporter and project-folder writer; `cli.py` is the entry point.

```bash
uv sync --project plugins/frc
uv run --project plugins/frc python functional_tests/cli.py            # all servers
uv run --project plugins/frc python functional_tests/cli.py nt4        # one server
uv run --project plugins/frc python functional_tests/cli.py sim systemcore --target fake # any subset (names: wpilog nt4 sim vscode jfr systemcore ctre-tools ctre-owlet ctre-passerine ctre-caniv ctre-diag)
uv run --project plugins/frc python functional_tests/cli.py ctre-tools --live   # also use CTRE's real website (a few spaced requests)
uv run --project plugins/frc python functional_tests/cli.py systemcore --target fake   # the fake controller only (never touches a real device)
uv run --project plugins/frc python functional_tests/cli.py systemcore --target real --host 172.30.0.1   # a real Systemcore, read-only
uv run --project plugins/frc python functional_tests/cli.py --keep     # keep the generated files
```

Needs no robot, network or model. Generated files go to `functional_tests/.output/` (git-ignored) and are removed after each run unless `--keep` is given. The exit status is 0 only if every check passed.
